# Changelog
## 0.1.0 - pre-alpha
- First public pre-alpha. It creates local backups and lets you download them. It does not restore anything yet.
- Installs on WordPress 6.5+ and PHP 7.4+, creates its own database tables and adds an admin menu. A System Info page reports what your server can do (archive formats, limits, folders).
- Back up now: choose database and files, pick ZIP (deflate), ZIP (store) or TAR.GZ (only formats your server supports are offered), and watch live progress with a cancel button.
- Built for cheap hosting: backups run in small resumable slices, survive timeouts and crashes, and split into parts (250 MB by default). Every backup writes a manifest.json next to its archives.
- Backups page: list your backups, download them through an authenticated link, lock a backup against deletion, delete or cancel one.
- Credentials the plugin will need later are encrypted at rest (libsodium); nothing is sent anywhere, the plugin makes no external calls.
- Known limits: no restore (a backup can only be downloaded and extracted by hand), no schedules or automatic backups, no retention, no Google Drive, S3-compatible or other remote destinations, no archive encryption, no email notifications, no settings or logs page.
- Backups are kept in a protected folder on the same server, so they do not protect you if you lose the server. Do not rely on this release as your only backup.

Honest per-feature status badges; unconfigured builds are `noindex`. Quality gates: tests, links, axe, Lighthouse, social images.
- Docker environment matrix (`tests/matrix/`): installs the built zip across PHP, WordPress, database and host profiles.
- Milestone 2 (data and security core), step 1: `Security\CredentialVault` (libsodium secretbox, `ovb1:` envelope, key from `OVB_ENCRYPTION_KEY` or WP salts, safe typed failure when the key changes) with `VaultException`, `Engine\JobState` (immutable JSON job state) and `Support\Manifest` (build and strictly validate `manifest.json`), with unit tests.
- Milestone 2 (data and security core), step 2: repositories for every plugin table (`BackupsRepository`, `BackupFilesRepository`, `DestinationsRepository`, `SchedulesRepository`, read methods on `LogsRepository`, shared `Database\Util`). All values are bound parameters, JSON columns decode safely, credentials are stored only as `CredentialVault` envelopes and never returned by normal reads (a changed encryption key marks the destination `needs_reconnect` instead of failing). Pure validation has unit tests; the Docker matrix now exercises every repository against real MySQL/MariaDB.
- Milestone 3 (backup engine), step 3a: engine core. `Engine\JobRunner` (resumable slices under an injectable `Budget`, per-backup `JobLock` in wp_options with stale takeover, state saved after every result, continuation through Action Scheduler, retries with backoff, stalled-job recovery every 5 minutes, cancel), `StepResult`/`JobContext`/`StepInterface`, step registry filter `ovb_engine_steps`, real `PreflightStep` (disk space, folders, format, contents) and `CleanupStep` (removes only `<local dir>/tmp/<uuid>`), `Archive\CapabilityDetector` (feeds System Info), `Support\Paths`. DB export, file scan, archive, encrypt, upload and retention steps are skipped until they are built. Unit tests for the pure logic; the Docker matrix runs jobs end to end against real MySQL/MariaDB (multi-run resumption, lock contention, stale lock, retries, recovery, cancel).

- Milestone 3 (backup engine), step 3b: resumable database export. `Engine\Steps\DatabaseExportStep` plus `Engine\Dump\*` (`SqlValueFormatter`, `TableInspector`, `SqlDumpWriter`, `BatchSizer`, `ExclusionRules`, `TableList`) write a one-statement-per-line `db.sql` (dump format documented in `docs/plan/04-backup-engine.md`) in adaptive batches with keyset paging and crash-safe resume (file cut back to the saved offset). Excludes plugin tables, `ovb_` options, transients, `excluded_tables` and the `ovb_backup_exclusions` filter. The Docker matrix imports the dump into a second database and compares every table.
- Milestone 3 (backup engine), step 3c: file scan and archiving. `Engine\Steps\FileScanStep` (resumable breadth-first walk, queue and list in work files, never follows symlinks, patterns `excluded_paths`, size cap `max_file_size_mb`, filter key `paths`; `Engine\Scan\*`) and `Engine\Steps\ArchiveStep` write `db.part01` / `files.partNN` archives and `manifest.json` into `<local dir>/backups/<date>_<uuid8>/` as ZIP (deflate or store, `ZipArchiver`) or TAR.GZ (`TarGzArchiver` + streaming `TarWriter`, no PharData, a file can span several runs), split at `part_size_mb` (default 250 MB, minimum 10), crash-safe resume, parts read back before they count as finished, one `ovb_backup_files` row per part. Entry-name contract for the restore (`abspath/`, `content/`, `db/db.sql`) is documented in `docs/plan/04-backup-engine.md`. TAR.GZ now needs only the zlib extension. The Docker matrix archives a 3,000-file fixture with 10 MB parts in all three formats over many slices with simulated crashes and compares the extracted tree with real `unzip` / `tar`.
- Milestone 3 (backup engine), step 3d: the user-facing end of a local backup. REST API `ovb/v1` (`Rest\RestController`: start, list, progress, cancel, lock, note, delete; capability + REST nonce on every route, validated args, 409 while another backup runs), pure `Engine\Progress` (percent from step bands + cursors, labels, ETA), the browser-driven kick (a progress poll runs one slice inline when nothing else is moving the job), `Security\DownloadController` + `DownloadHelper` (authenticated streaming with nonce, containment, single HTTP Range, 1 MB chunks), `Backups\BackupFiles` (row to path, safe folder delete), Backup Now page (contents, formats the server really supports, live progress, cancel, summary with downloads), History page (`WP_List_Table`: download list, lock, unlock, delete, cancel, log link), `Admin\Assets` and small ES5 scripts and CSS in `assets/admin/`. Real-HTTP end-to-end checks in the Docker matrix (`tests/matrix/http-e2e.sh`).
