# 08 – Restore

## Sources
1. From history (local or any destination) – MVP
2. Uploaded archive via chunked browser upload – Phase 2
3. Archive placed on server via FTP ("scan folder") – Phase 2
4. Remote re-index after fresh install (reads manifest.json) – Phase 2
5. Standalone restorer when wp-admin is broken – Phase 3

## Flow (resumable job)
1. Download parts to temp dir → verify SHA-256 checksums.
2. Decrypt if needed (ask password).
3. Show what will be restored; user chooses full / DB only / files only / selective (P2).
4. **Safety snapshot** of current state (DB + affected folders).
5. Maintenance mode on (auto-expire after 30 min failsafe).
6. Restore DB (chunked import; prefer import into temp prefix then swap).
7. Restore files (skip own plugin folder).
8. Maintenance off, flush caches/rewrite rules, show result page with "Undo restore" (uses safety snapshot).

## Self-preservation (SelfPreserver)
- Before DB import, export `ovb_*` tables + `ovb_settings` + destination credentials; re-apply after import.
- Never overwrite `wp-content/plugins/openvault-backup/`.
- Keep the running restore job record alive across the DB swap.
- Expect the admin session to be invalidated → result page must handle re-login.

## Edge cases to plan for
- Different table prefix in backup vs site
- Backup from a different domain (Phase 3 migration)
- Newer plugin version backups opened by older plugin (manifest version check)
- Not enough disk space for download + extract (preflight)

## Implemented in Milestone 5 step 5a (restore engine core: job, fetch, verify, preflight, plan)

Scope of the milestone: restore **from history** only (a backup that exists in this site's `ovb_backups` / `ovb_backup_files`, from the local copy or from any destination): whole site, database only or files only. Restore from an uploaded archive is not part of it. The database is restored **in place** after a safety snapshot (the dump drops and recreates each table). Step 5a builds the foundation and **changes nothing on the site**: no database import, no file extraction, no maintenance mode, no UI (steps 5b to 5d). `RestoreManager::start()` runs the checks, creates the job and queues it; the job runs `preflight`, `fetch` and `verify` and then stops with the status `verified`.

### Job record
- Table `{prefix}ovb_restores` (migration 2, docs/plan/03): see there for the columns. It is a table because a database import recreates `wp_options` and drops the `ovb_*` option rows, while every `ovb_*` table survives (the dump excludes them).
- State is an `Engine\JobState` (cursor under 64 KB, meta under 16 KB), extended with the restore steps `fetch`, `verify`, `snapshot`, `db_restore`, `file_restore`, `finish`. The meta (`Restore\RestoreMeta`) holds only `restore_id`, `mode`, `ack` (acknowledged warnings), `tried` (sources that failed) and, later, `confirmed`. The plan is never stored: each slice rebuilds it from the database and the disk.
- Statuses: `queued` and `running` (a runner has work), **`verified`**, `complete`, `failed`, `cancelled`. `verified` means: everything is downloaded and checked, the job holds no lock, queues no action and keeps its work folder; it waits for the user to confirm the changes (the flag `confirmed` in the meta, set by the confirm action of step 5c). Until then it stays `verified`; if the flag were set while a later step has no implementation the job fails with a clear message. A `verified` job is *active* (no second restore may start) but not *running* (it does not block a backup).

### Restore plan (`Restore\RestorePlan`, pure)
Built from the backup row, every `ovb_backup_files` row of the backup, the parsed `Manifest`, the mode, the files found in the local backup folder, and the sources that already failed.
- Parts per mode (manifest part kinds): `full` = all parts, `db` = `db` parts, `files` = `files` and `other` parts. A mode the backup cannot serve (for example `db` for a files-only backup) has no parts and is refused by the preflight.
- **Source preference** (documented rule): 1. the local copy (destination id 0), complete when `manifest.json` and every needed part exist in `<local dir>/backups/<folder>/` with the size the manifest records; 2. then each destination in ascending id, complete when `manifest.json` and every needed part have a row with `upload_status` `done` and a `remote_ref`. A destination holding only some of the files is ignored. A source that failed (the `tried` list) is skipped, so a damaged local copy falls back to the next copy once.
- Estimates: download = needed bytes + manifest, only when the chosen source is not local; extract = db parts x 5, files parts x 2 (x 1 for `zip-store`); safety snapshot = the size of the needed parts; free space needed = download + extract + snapshot + the "minimum free space" setting (`min_free_space_mb`, default 100; 0 switches the disk check off, as for backups).
- `summary()` has the facts the restore page will show: backup id, uuid, creation time, trigger, format, encrypted flag, plugin / WordPress / PHP version, site URL, table prefix, contents flags, db and files part counts and bytes, what the mode restores.
- `Restore\PlanLoader` is the thin impure side: it finds a valid manifest (work folder copy, local folder, then destinations in id order; a manifest read from a destination is saved into the work folder), checks that it belongs to the backup (uuid) and builds the plan. A manifest of a newer schema stops the search at once and is reported as "created by a newer version".

### Preflight (`Restore\RestorePreflight`, pure rules plus a collector of real facts)
`RestoreManager::start()` runs it before anything is created; the job's `preflight` step runs it again when the job starts. Result: `{ ok, errors[], warnings[], requires_ack[] }`, each entry `{ code, message }`.
- **Errors** (the restore does not start): backup missing or not finished; manifest unreadable; manifest `plugin_version` newer than the running plugin, or a newer manifest schema ("created by a newer version of OpenVault Backup, update the plugin first"); `encrypted` (Phase 2); a backup or another restore is active; the table prefix of the manifest differs from `$wpdb->base_prefix` (**refused**: restoring to a different prefix is not supported yet; a files-only restore ignores this); the mode needs parts the backup lacks; no source holds a complete copy (the reasons per source are listed); local folder not writable; the destination of a remote source needs a reconnect (the reconnect message) or fails `test_connection()`; not enough free disk space (`Not enough free disk space: X free, Y needed.`; when `disk_free_space()` is unavailable it warns and continues).
- **requires_ack**: the manifest `site_url` differs from this site's `siteurl` (scheme, host, port and path are compared, case and a trailing slash ignored). A database restore would carry the old address into links, images and settings; migration with search-replace is Phase 3. It blocks until `start( ..., array( 'acknowledge_url_mismatch' => true ) )`; the acknowledgement is stored in the job meta and the job's own preflight accepts only an acknowledged job. A files-only restore skips this rule. An acknowledgement never overrides an error.
- **Warnings**: WordPress or PHP major.minor differs from the backup's (a newer WordPress in the backup is worded more strongly), a `full` restore of a backup with only files or only the database, unknown free disk space.

### Fetch and verify (`Restore\Steps`, resumable)
- Work folder `<local dir>/tmp/restore-<id>/` (`Restore\RestoreWorkDir`): created with the guard files, plain file names only, removed only when the path is `tmp/restore-<digits>` directly inside `tmp/` (pure check plus realpath comparison and a symlink refusal). The plugin's tmp area is never wiped wholesale; other folders in it (the uuid work folders of backups) are never touched.
- `FetchStep`: when the chosen source is the local folder nothing is copied (the files are read and verified in place). Otherwise `manifest.json` and the needed parts are downloaded through `DestinationInterface` into `<name>.part` files and renamed when complete; files already there with the right size are skipped. The sink writes chunk by chunk (1 MiB Local, 8 MiB S3) and stops when the `Budget` is exhausted. Resume: the cursor `{ i, off, tries, n }` names the file and the byte offset; a new slice truncates the `.part` file to `min( saved offset, bytes on disk, file size )` (garbage written by a killed run after the last saved cursor is discarded) and continues there. Destinations that implement the new optional `Destinations\ResumableDownloadInterface::download_from( $ref, $offset, $sink )` (Local and S3 do) read from the offset; for the others the first bytes are read and skipped (correct, but re-read from the provider). A retryable `DestinationException` is retried 3 times with the upload backoff (30 s, 120 s) through `StepResult::wait()`; a permanent one, a third failure or a file that ends with the wrong size marks the source as tried and the job continues with the next complete source (once per source) or fails naming the file.
- `VerifyStep`: for every file of the chosen source: size equals the recorded size, SHA-256 equals the manifest's (and the database row's, which must agree), `manifest.json` is valid (`Manifest::from_json()`), has the backup's uuid and matches the checksum of its row; links and missing files are damage. **Hashing limit**: a part is hashed in one go with `hash_file()` because PHP 7.4 cannot save a hash context; the budget is checked between files, so a slice may overrun by the time one part takes to read (parts are capped by the "part size" setting, 100 MB by default, about a third of a second at 300 MB/s). A damaged file makes the source tried: downloaded files of that source are deleted, the job jumps back to `fetch` with the next complete source (once per source) or fails: "The backup file X is damaged: the checksum does not match. No other complete copy is left. Start the restore again to download it again, or choose another backup."
- On success the meta gets `verified = { source, files, bytes, at }`.

### Runner (`Restore\RestoreRunner`)
Built on `JobState`, `StepResult`, `Budget`, `JobLock` and Action Scheduler like `Engine\JobRunner`, over `RestoresRepository`.
- Action `ovb_run_restore` (argument: restore id), group `openvault-backup`; step registry filter `ovb_restore_steps`; step order `preflight, fetch, verify, snapshot, db_restore, file_restore, finish`. Only the first three exist in 5a. A step may jump: `next_step()` with a state that already names another step (verify to fetch).
- **Lock / exclusion** (documented key): one global lock for restore slices, the option `ovb_lock_restore` (`JobLock` now accepts a lowercase name next to a backup id; `ovb_lock_restore_start` guards the check-and-create of a start). Only one restore may be active, so a per-restore lock adds nothing. A restore also excludes backups: `RestoreManager::start()` refuses while a backup is queued, running or uploading (`find_incomplete`), and `POST /ovb/v1/backups` returns 409 `ovb_restore_running` while a restore is queued or running (a `verified` restore does not block it). The scheduler of Phase 2 must make the same check.
- Failure rules are the backup runner's: a thrown error is an attempt (3 attempts, 30 s and 120 s backoff), `StepResult::fail()` fails at once, a `continue_step()` that does not move the cursor counts as an attempt; failure and cancel remove `tmp/restore-<id>` and drop the pending actions.
- Stalled jobs: `RestoreRunner` hooks the same 5-minute `ovb_recover_stalled` action as the backup runner; a `queued` / `running` job without a heartbeat for 10 minutes is re-queued (3 times, then failed). A `verified` job is never touched.
- `cancel()`: status `cancelled`, error "Cancelled by user", work folder removed, a run that is active notices after its current slice and stops.

### Manager (`Restore\RestoreManager`)
`start( $backup_id, $mode, $options )` returns `{ ok, restore_id, errors, warnings, requires_ack, plan }`: on success `ok` is true and `restore_id` >= 1 (the job exists and is queued), otherwise it is the structured preflight failure with `restore_id` 0 and nothing created. Options: `acknowledge_url_mismatch`, `user_id`. Capability and nonce checks belong to the REST/admin callers of step 5d. `cancel( $id )` delegates to the runner.

### Limits and risks of 5a
- A `verified` job keeps its downloaded files until it is applied or cancelled; nothing expires it yet.
- Providers without `ResumableDownloadInterface` re-read the part from the start on every slice; fine for the built-in providers, slow for a large file on a third-party provider.
- A part is hashed in one go (see above).
- The exclusion between a backup start and a restore start is a database fact (status) plus the existing start guards, not one shared lock; two requests starting a backup and a restore in the same instant could both pass their checks (the preflight of the restore job and the per-job locks still apply).
- RemoteIndexer and UploadReceiver are still stubs (Phase 2); FileRestorer was built in step 5c (below). SelfPreserver, SafetySnapshot, MaintenanceMode and DatabaseImporter are implemented in step 5b (below), which also makes the import preserve the `ovb_lock_*` rows.

## Implemented in Milestone 5 step 5b (database restore: snapshot, maintenance mode, self-preservation, safe import)

Scope: a **database-only** restore (mode `db`) works end to end, from history, on a single site. Modes `files` and `full` were refused by the preflight until step 5c (they work now, see "Implemented in Milestone 5 step 5c" below), and a database restore on a multisite network is refused (`multisite_unsupported`: "Restoring a multisite network is not supported yet"). There are still no REST routes and no UI for restore (step 5d); the engine is driven through `RestoreManager` (`start()`, `confirm()`, `cancel()`) and `RestoreRunner`.

### Flow
`preflight, fetch, verify` (5a) park the job at `verified`. `RestoreManager::confirm( $id )` (the user's go) sets the meta flag `confirmed`, moves the job to `running` and queues it; it is refused when the restore is not waiting for confirmation (`not_verified`) or a backup is running (`backup_running`). Then: `snapshot` (a real backup of the current database), `db_restore` (unpack, validate, import), `file_restore` (skipped for mode `db`; unimplemented until 5c, a job that would need it fails clearly), `finish`. `RestoreRunner::is_skipped( $step, $meta )` is the one place that decides which steps a mode passes over (`file_restore` for `db`, `db_restore` for `files`).

### Safety snapshot (`Restore\SafetySnapshot`, `Steps\SnapshotStep`)
- A **real backup** through the normal engine: `trigger_type` `pre-restore`, contents `{ db: true }` (never the files: a files restore is protected by the undo journal of step 5c instead, `SafetySnapshot::contents_for_mode()`), the format of the backup being restored when this server supports it, else the default format, local folder only, **locked at creation** (retention and manual delete leave it alone; a failed snapshot is unlocked again), note "Safety snapshot before restore #<restore id>". It is linked through `ovb_restores.snapshot_backup_id` and the job meta (`snapshot`: `{ id, at }`), written at once so a retry never starts a second one. History shows it like any backup with the label "Safety snapshot before restore". "Undo restore" (5d) is an ordinary restore from that backup.
- The step waits for it (`StepResult::wait`, 3 s polls, 2 hours at most) and **fails the restore if the snapshot fails, vanishes or only ends `partial`**: the job never goes on to `db_restore` without a `complete` snapshot (message: "The safety snapshot failed. ... The restore was stopped before anything was changed.").
- **Exclusion between backups and restores**: users cannot start a backup while a restore is queued or running (REST 409 `ovb_restore_running`, unchanged). The snapshot is the one backup that must run inside a running restore, so `SafetySnapshot::create()` writes the backup row and starts the engine job directly instead of going through that route: this is the explicit internal bypass (the engine itself has no such guard; the matrix checks that a REST backup stays refused while the internal snapshot completes). `RestoreManager::confirm()` refuses while a backup is running.

### The dump is untrusted: the statement whitelist (`Restore\DumpValidator`, pure)
A backup may sit in a bucket or folder that somebody else can write, and a restore runs its statements with the site's database rights. **Nothing reaches the database unless `DumpValidator::check()` accepts the line.** The importer reads the dump line by line (one statement per line, as `SqlDumpWriter` writes it; a line is limited to 4 MB, the writer keeps statements near 512 KB) and accepts only:
- empty lines and comment lines `-- ...` (never executed; `-- key: value` header lines are read, `-- ovb-dump-end` is the end marker);
- `SET NAMES <utf8mb4|utf8mb3|utf8|latin1|ascii|binary>`, `SET FOREIGN_KEY_CHECKS=0|1`, `SET UNIQUE_CHECKS=0|1`, `SET sql_mode='<list>'` (modes from a short list that never contains `NO_BACKSLASH_ESCAPES`, `ANSI_QUOTES` or `ANSI`, because the tokenizer assumes backslash escapes), `SET time_zone='+00:00'`; every other `SET` (`GLOBAL`, `@@global`, `PASSWORD`, `@var`, `SESSION`) is refused;
- `` DROP TABLE IF EXISTS `t` ``;
- `` CREATE TABLE `t` ( ... ) ... `` on one line: no `;` outside a string literal, no comment of any kind (the one exception is the exact text `/*!80016 DEFAULT ENCRYPTION='N' */` that MySQL 8 adds), no backslash outside a literal, no `schema.table` name, no reference to a plugin table, `ENGINE` limited to InnoDB, MyISAM and Aria (so no FEDERATED or MERGE), and none of the words `SELECT, OUTFILE, DUMPFILE, LOAD_FILE, LOAD, DIRECTORY, TRIGGER, PROCEDURE, FUNCTION, EVENT, GRANT, PASSWORD, CONNECTION, SLEEP, BENCHMARK, HANDLER, CALL, PREPARE, EXECUTE, TABLESPACE, USER, DROP, CREATE, INSERT, TRUNCATE, RENAME, ALTER, USE, UNION, INTO` outside literals. Words inside string literals are data. Partitioned tables (`/*!50100 PARTITION ...*/`) are therefore refused (honest limit);
- `` INSERT INTO `t` [(`col`,...)] VALUES (v,...),(v,...); ``: the VALUES part is read with a real tokenizer (strings with backslash escapes and doubled quotes, `NULL`, numbers, `0x<hex>`; no spaces, no functions, no comments). `;`, `--`, `/*` and quotes inside a string are data; the same text outside a string is a refusal. A stacked second statement is impossible because the line must be exactly one INSERT.
- Table names: letters, digits, `_`, `$`, at most 64 characters, they must start with the site's `$wpdb->base_prefix` (exact case) and must not start with `<prefix>ovb_` (the plugin's own tables, any letter case: MySQL on Windows and macOS is case-insensitive). A violation names the **line number** and a fixed reason, never the statement.

The same whitelist runs twice: in a **validation pass** that executes nothing (see below) and again, line by line, during the import. Also refused: NUL, CR, invalid UTF-8, data after the end marker, statements out of order (`INSERT` before its `CREATE`, a statement for another table than the last `DROP`).

### `db_restore` phases (`Steps\DbRestoreStep`, cursor key `ph`)
1. `x` **unpack**: `Archive\ArchiveReader` streams exactly `db/db.sql` (an allow-list of one name, checked for `..`, absolute paths, backslashes, NUL) out of the `zip`/`zip-store` part (ZipArchive `getStream`) or the `tar.gz` part (`gzopen` plus `TarWriter::parse_header()` / `parse_pax()`: PAX long names and sizes, base-256 sizes; only a regular file with the exact name counts) into `<work folder>/db.sql` in 256 KB chunks. Resume is by byte offset: a compressed stream cannot seek, so the bytes before the offset are read and dropped again (decompression only; that time is not part of the budget); the destination is first cut back to the offset, so bytes written by a killed run are discarded. The size must match the archive. Before the first byte the part is hashed again (it may have changed since `verify`) and the free disk space is checked.
2. `v` **validate**: `DatabaseImporter::validate_slice()` judges every line without executing anything. A refused line fails the restore with its line number and "Nothing was changed. The backup may be damaged or may have been tampered with." This pass also proves the dump is complete (end marker), was made with this site's prefix (`-- table-prefix:` header) and records the longest statement, compared with `max_allowed_packet`. When it passes, the plugin's own option rows are captured (SelfPreserver), the maintenance flag is switched on and the cursor moves on. **Cancel is possible in phases x and v and refused from phase i on** (`RestoreRunner::cancel_refusal()`, also checked by `RestoreManager::cancel()`).
3. `i` **import**: `DatabaseImporter::import_slice()` runs the dump through `$wpdb` (`WpdbExecutor`: errors hidden, `SAVEQUERIES` memory use dropped, only the MySQL error number is read; the connection is prepared with utf8mb4 and UTC and put back afterwards). The dump's tables are imported in place (drop, create, insert): tables that exist now but not in the backup are left alone. **Action Scheduler tables (`<prefix>actionscheduler_*`) are validated but never touched**, because the restore itself runs through Action Scheduler (replacing its queue would delete the running job's own action); `<prefix>ovb_*` is refused by the validator.

### Resume safety (the cursor)
Cursor (under 400 bytes): `off, ln` (byte offset and lines consumed), `tb` (dump table in progress), `to, tl` (offset and lines in front of that table's `DROP TABLE`), `cr, cl` (created, clean), counters `td, rw, st, rt, sc, sk`. It is stored in the restore job state **after every executed statement** (the step saves through `RestoresRepository` directly, not only when the slice returns). INSERT is not idempotent, so a slice first stores the cursor with `cl = false` before it runs anything, and only a slice that stops on its budget returns `cl = true`. A resume that finds `cl = false` while a table is in progress goes **back to that table's `DROP TABLE` line** and imports the table again: no duplicates, at the price of re-importing one table. Proven by a unit test that kills the importer after every statement of a dump and by the matrix (three kills in the middle of a real import). A lost connection (errors 2006 and 2013) is retried with the runner's backoff (`StepResult::wait`, 3 attempts); every other statement error fails the restore.

### The options table, the job lock and self-preservation (`Restore\SelfPreserver`)
- The options table is imported into the shadow table `<prefix>options_ovbnew` and swapped in with one atomic `RENAME TABLE` after its last statement (a resume redoes the table from its `DROP` line, so the swap is idempotent). Just before the swap the plugin's live rows are captured again (the running job's lock row is current), right after it they are written back, so the running job never sees an options table without them.
- Kept across the import: every option whose name starts with `ovb_` (settings, `ovb_local_dir`, `ovb_db_version`, `ovb_installed_at`, `ovb_lock_*` including `ovb_lock_restore`, `ovb_recovery_checked`, ...), the Action Scheduler state rows (`action_scheduler_*`, `schema-ActionScheduler_*`), this plugin's entry in `active_plugins` (added when the backup's list lacks it, the backup's other plugins stay), and, only with the job option `keep_site_urls` together with the acknowledged URL mismatch, the current `siteurl` and `home`. `keep_site_urls` is a safety valve so the restored site stays reachable on its current domain, **not a migration**: serialized data in the dump still carries the old address (search-replace is Phase 3). The login of the user who started the restore is recorded as metadata for the result page (a session cannot be kept: the users table is replaced).
- The rows are held in `<work folder>/self-preserve.json` (values base64 encoded), not in the database that is being replaced and not only in memory. `apply()` deletes plugin rows that came from the backup, writes the kept rows, fixes `active_plugins`, re-applies the URLs, deletes `rewrite_rules`, flushes the object cache and **reads everything back from the database**; a difference throws and fails the restore. `verify()` repeats the read-back at the end (job locks and throttles are compared by existence only). The `ovb_restores` row, its state and every other plugin table survive by themselves: they are never dropped.

### Maintenance mode (`Restore\MaintenanceMode`)
The usual `.maintenance` file is evaluated before plugins load and would also block the plugin's own progress polling and the Action Scheduler requests that run the restore, so the plugin has its own flag: `<local dir>/maintenance.json` = `{ restore_id, started, expires }` (a file, not an option: the options table is being replaced). It is switched on when the dump passed validation, refreshed every slice and by the finish step, and removed by `finish` (and on plugin deactivation). It **expires on its own 30 minutes after the last refresh**; a malformed flag, or one with an expiry more than twice the TTL away, counts as off (fail open). While it is valid the plugin hooks `plugins_loaded` (priority 0) and decides per request (the 503 page itself is sent on `init`, priority 0, because translations must not load earlier) (`decide()`, pure):
- always allowed: WP-CLI/CLI, `wp-login.php`, REST routes of `ovb/v1`, `admin-ajax.php` with an action `ovb_*` or `as_async_request_queue_runner` (the loopback request that runs the next slice);
- `wp-cron.php` runs, but only the cron event `action_scheduler_run_queue` (filter `pre_get_ready_cron_jobs`), so the restore keeps going when loopback requests are blocked while every other scheduled event waits. Known limit: that queue run also executes other plugins' Action Scheduler actions;
- admin area requests (wp-admin, `admin-post.php`, other `admin-ajax.php` actions) only for users with `manage_options`, checked on `init`;
- everything else (front end, other REST routes, `xmlrpc.php`): `503 Service Unavailable`, `Retry-After: 120` and a small branded page.

The REST route is recognised from the path or from `rest_route=` in the query only (a path in a query value does not count: a unit test found this bypass and pins it). While the users table is recreated an administrator cannot be recognised for a few milliseconds and sees the 503 page; the progress screen of 5d must retry. After a failed restore the flag is not refreshed, so the maintenance page ends 30 minutes after the last slice unless the user restores or undoes sooner; `MaintenanceMode::status()` / `is_active()` exist for the admin notice of 5d.

### Failure and result
- Before the import starts a failure says "Nothing was changed". Once it runs, a refused line or a statement error fails the restore with: "The restore stopped part way. Your site may be in a mixed state: use Undo restore (safety snapshot, backup #N) or restore again." plus the line number, the table name and the MySQL error number (never a statement or a value). The snapshot stays; maintenance mode stays on until it expires.
- `finish`: verifies the kept settings once more, switches maintenance off, flushes the object cache, deletes `rewrite_rules`, stores `result` in the job meta (`tables`, `statements`, `rows`, `skipped`, `seconds`, `snapshot_id`, `kept_urls`, `user`), logs a line, removes the work folder. The runner then sets the status `complete`.
- `cancel()`: safe until the import starts (also while the snapshot is being taken: the snapshot job is stopped, a finished snapshot stays locked); afterwards refused with the text above.

### Limits and risks of 5b
- A restore replaces the tables of the dump; tables created after the backup stay. A restore that fails half way can only be undone through the snapshot.
- Resuming an interrupted table re-imports that whole table. A 1 GB table interrupted at its end is imported again.
- Unpacking re-reads the bytes before the saved offset on every slice (decompression time, not part of the budget).
- A statement larger than `max_allowed_packet` is detected before anything changes; a single row over 4 MB is refused by the line cap.
- Dumps with partitioned tables, triggers, views, stored routines, other storage engines or `schema.table` names are refused by design. Collations the target server does not know (a MySQL 8 dump on MariaDB) fail with the database error number.
- The options swap runs inside one slice; a crash exactly between the rename and the write-back leaves the job's lock row missing, which the stalled-job recovery repairs by running the job again.
- The matrix proves the engine against real MySQL and MariaDB with zip and tar.gz parts; the maintenance page is checked over real HTTP; step 5d adds the REST routes and the screens.

## Implemented in Milestone 5 step 5c (file restore, rollback journal, undo)

Scope: modes `files` and `full` work end to end, from history, on a single site; every restore of files can be **undone**. Still no REST routes and no UI (step 5d): the PHP API is `RestoreManager::start()`, `confirm()`, `cancel()`, `can_undo()`, `undo()` and `dismiss_undo()`. A multisite network and an encrypted backup are still refused (for every mode, including `files`). Restoring from an uploaded archive is not part of the milestone.

### Steps, skipping and cancel
Step order: `preflight, fetch, verify, [confirm gate], snapshot, db_restore, file_restore, file_undo, finish`. `RestoreRunner::is_skipped()` decides per job from the mode and from two meta flags the manager records from the plan (`has_db`, `has_files`: a `full` restore of a backup without a database part has no database steps and no snapshot):
- `snapshot` runs only for jobs that change the database (`db`, `full`). A **files-only restore takes no snapshot**: the undo journal is its recoverable state (a snapshot of the files would copy the whole site). A `full` restore has both: the database snapshot and the journal. The gate in front of `snapshot` still applies to every mode (the user confirms once).
- `db_restore` runs only with a database change; `file_restore` only with file changes; `file_undo` only in an undo job that has files to put back; `preflight, fetch, verify` are skipped by an undo job without a database snapshot (nothing to download).
- **Cancel** (`RestoreRunner::cancel_refusal_for( $step, $cursor, $meta )`, pure): allowed until the first change, i.e. in front of the gate, during `snapshot`, and in the setup phase of `file_restore` / `file_undo` of a job that does not change the database; refused from the import (`db_restore` phase `i`), in the apply phase (`ph` = `a`) of the file steps, in any file step of a job that also changes the database, and in `finish`. A cancel that succeeds switches maintenance mode off again when the flag belongs to that restore (a setup that died after enabling it).
- **Maintenance mode applies to every mode**: the file steps switch it on in their setup phase (it already is after a database import), refresh it every slice, and `finish` switches it off. After a failure it stays on until it expires (30 minutes), like after a failed database import.

### Safe extraction (the core risk)
An archive is untrusted (a bucket or folder that somebody else can write; the checksums do not help, an attacker rewrites them too) and so is the destination tree (a symlink planted in `uploads`). The work is split so the decisions are pure and unit tested:
- `Archive\EntryWalker` reads the entries of a part in order with their TYPE (file, folder, symlink, hardlink, special), size and mtime: zip through ZipArchive (Unix mode in the external attributes; the stream is opened by name because `getStreamIndex()` only exists from PHP 8, so two entries with the same name are refused), tar.gz through `gzopen()` and `TarWriter::parse_header()/parse_pax()` (PAX path, size and mtime, GNU long names; the body of a link or device is never read). Resume is by entry count (below).
- `Restore\ExtractionPolicy` (pure) maps an entry to a destination or says why not. **Mapping**: `abspath/<rel>` and `content/<rel>` through the roots of the backup's contents flags (`ContentSelector`), so a relocated plugins/themes/uploads/mu-plugins folder is put back where it lives now and only the roots the backup contains are ever touched (a shallow root takes no deeper path, a file root exactly its name). `db/` entries are never extracted here.
- **Rejected** (counted, logged by entry number with a cleaned, 80 byte name; never fail the restore): any `..`, `.` or empty segment, a leading `/`, a backslash, NUL or any control character, a drive letter, bidirectional-control characters (right-to-left override and friends), a segment ending in a dot or space, `:` in a segment on a Windows host, invalid UTF-8, more than 1024 bytes; symlinks, hardlinks, devices, fifos and any other special entry (reasons `name_unsafe`, `name_long`, `link`, `special`).
- **Protected paths** (skipped, counted by reason; compared case-insensitively): the plugin's own folder (`OVB_PATH`, its real path, and `<plugins>/openvault-backup`: `protected_plugin`), the plugin's storage folder and any `wp-content/ovb-*` (`protected_storage`), `wp-config.php` wherever it lives (`protected_config`), `.maintenance` (`protected_maintenance`), and `.htaccess`, `web.config`, `php.ini`, `.user.ini` in the WordPress folder (`protected_server`). **Why wp-config.php is never restored**: it holds this site's database credentials and keys, and an old copy can lock the owner out; it is shown in the preflight as "will NOT be restored" (warning `wp_config_skipped`, also `server_config_skipped` and `plugin_protected`). **Server configuration files** are skipped by default for the same reason (a wrong `.htaccess` takes the site down); the job option `restore_server_config` (`RestoreManager::start( ..., array( 'restore_server_config' => true ) )`) opts in. Only the files directly in the WordPress folder are protected: an `.htaccess` inside `uploads` is an ordinary file, and PHP files in uploads are restored like any other file (documented, not blocked).
- Before the first write the step runs a **self-test** (`ExtractionPolicy::site_self_test()`, writes nothing): entries that map into the plugin's folder, its storage folder, wp-config.php and the other protected places must be refused by a policy with every content flag on; otherwise no file is restored (`Nothing was changed`).
- `Restore\SafeWriter` does the file system work and trusts nothing below a root. **Roots** (uploads, plugins, wp-content, the WordPress folder ...) come from WordPress and are trusted, also when the site owner links one elsewhere. Every folder BELOW a root is walked component by component: an existing symlink is refused (`dest_symlink`), a file in the way of a folder (`dest_not_dir`) and a folder in the way of a file (`dest_is_dir`) too; missing folders are created one by one (mode `FS_CHMOD_DIR` or 0755) after their journal line; the real path of the final folder must lie inside the real path of the root. The target itself is never written through: a symlink target is refused. A file is written to `<name>.ovbtmp<token>` in the same folder (created exclusively: a planted link or file at that name is removed, never followed) and renamed over the target (atomic on one file system; where rename cannot replace, unlink then rename: the original is already saved); mode `FS_CHMOD_FILE` or 0644 and never an execute bit; the archive's mtime is kept (zip: two second resolution). A short write is a full disk.
- **Semantics**: files in the backup OVERWRITE files on the site, missing ones are ADDED. Nothing on the site is deleted (leftovers of later installs remain; an opt-in "remove files not in the backup" is not part of this milestone). Empty folders and empty folder entries are not restored; permissions and owners are not restored (the site's defaults).

### The file restore step (`Steps\FileRestoreStep`, id `file_restore`) and `Restore\FileRestorer`
- Phase `s` (setup, nothing is written to the site): self-test, create the undo journal, switch maintenance mode on. A failure says "Nothing was changed". Phase `a` (apply): `FileRestorer::restore_slice()` walks the files parts in plan order within the `Budget`. Each part is hashed again before its first entry (it may have changed since `verify`).
- Resume: cursor `{ p part, e entries done in the part, o bytes of the entry in progress that are in its temp file, fl files written, by bytes, cr created, ow overwritten, sk {reason: count}, ef failures in a row, lg lines logged, sj skip lines journaled }` (under 500 bytes), saved every 50 entries by the step. A slice reads the part again and skips the `e` entries that are done: for **tar.gz this means decompressing the entries before it again in every slice** (the compressed stream cannot seek; counted, not written; the cost grows with the part size, which the part-size setting caps), zip jumps by index. A file that does not fit in the budget is written in 256 KB chunks across slices: the temp file is cut back to `min( o, its size )`, the bytes before it are read and dropped, the copy goes on (a file larger than the budget is therefore resumable, but the first bytes are decompressed again). Entries that a slice completed before it died without saving its cursor are simply done again: same content, and the journal keeps the first saved original.
- Errors: one entry that cannot be written (`write_failed`, a symlinked or blocked destination, a damaged entry) is counted and skipped. **Systemic** errors stop the restore with `The restore stopped part way. Some files were already replaced: use Undo restore (it puts the replaced files back) or restore again.` plus the reason: the disk is full (`disk_full`, also checked up front for a file larger than the free space), the undo journal or an undo copy cannot be written (`journal`, before the destination is touched), 25 write failures in a row (`unwritable`), a part that changed after verification (`part`), a damaged or cut-off part (`archive`). Maintenance mode stays on and the journal stays, so Undo works. The verification of the files is the part checksum (SHA-256, checked in `verify` and again before the part is read) plus the size: a written file must have exactly the size of the entry.
- Result in the job meta (`files`, copied into `result.files` by `finish`): `restored, created, overwritten, bytes, parts, skipped {reason: count}, skipped_n`; `result.journal` says whether an undo journal exists, `result.mode` the mode. Counts only: no names, no content, no paths.

### The rollback journal and undo data (`Restore\UndoJournal`, `Restore\UndoStore`)
- Location: `<local dir>/undo/restore-<id>/` inside the protected storage folder (guard files at each level this class creates; never archived, never written by a restore). `journal.log` is append-only UTF-8, TAB separated, one line per action, flushed (and fsynced where PHP can) BEFORE the action happens (write-ahead): `H 1 <restore id> <time> <json contents flags>` header; `O <entry> <size> <sha256>` an existing file is about to be overwritten (its original was copied first, to `files/<entry>`, streamed with the SHA-256 computed while copying, written under a temporary name and renamed); `C <entry>` a file is about to be created; `D <entry>` a folder is about to be created; `S <url-encoded name> <reason>` informational skip lines (at most 500; the name is cut and URL-encoded so a hostile name cannot inject a line). `<entry>` is the archive entry name (`content/uploads/a.jpg`): root and relative path in one, validated with `EntryName::is_safe()`. Absolute paths are never stored: undo recomputes the roots from the header's contents flags.
- A line counts only with its newline: a fragment left by a crash is ignored. "The first saved copy is the original": a file that is processed again after a crash is not saved again, so `[C][O]` (created, then seen again as existing) replays to "removed" and `[O][O]` restores the same copy twice.
- **Cost**: the size of the files that were overwritten (not the whole site), kept after a successful restore until `dismiss_undo()`. Nothing deletes it automatically yet (retention milestone). The preflight estimate (`RestorePlan::journal_bytes()`, an upper bound because it is unknown up front which files exist): the files parts x 2 (x 1 for zip-store); every file is either new (it grows the site) or overwritten (its original is copied), never both, so the same number covers both and is part of `extract_bytes()`. Required free space = download + database unpack (x 5) + files (x 2) + snapshot (the database parts; none for `files`) + the margin setting; the error text is the usual "Not enough free disk space: X free, Y needed.".

### Undo (`RestoreManager::undo()`, `Steps\FileUndoStep`)
- `can_undo( $restore_id )` returns `{ ok, code, message, undo_db, undo_files, snapshot_id, journal }`; the pure rules are `RestoreManager::undo_eligibility()`: refused (with a code and message) for a restore that does not exist (`restore_missing`), an undo job (`not_undoable`: an undo is not itself undoable), one already undone (`already_undone`) or dismissed (`dismissed`), one that is not finished (`not_finished`: queued, running, verified, cancelled), one that changed nothing (`nothing_to_undo`), a missing or failed safety snapshot when the database was restored (`snapshot_gone`), a missing journal when files were restored (`journal_gone`), and while a backup or another restore runs (`backup_running`, `restore_running`). A **failed** restore can be undone when the database import began (`db_started` in its meta) or the journal records an action.
- `undo()` creates a NEW job of mode `undo` (the `ovb_restores.mode` column accepts `undo`; no new table) whose meta holds `undo_of`, `has_db`, `has_files`, `confirmed` and the acknowledged address mismatch (the snapshot is this very site, so its address is not a surprise); it needs no second confirmation. Same return shape as `start()`: `{ ok, restore_id, errors, warnings, requires_ack, plan, undo_db, undo_files }`. Steps: `preflight, fetch, verify` (the snapshot is an ordinary local backup: a database plan on the snapshot backup, so the same checks, checksum verification and dump validation apply), `db_restore` (the same step, same safety rules, maintenance mode, self-preservation), `file_undo`, `finish`.
- **No new snapshot is taken for an undo** (the simpler safe option): the state being abandoned is the state the user chose to leave, the snapshot being restored stays locked, a failed undo can be run again (the original stays undoable until an undo completes), and a snapshot of a snapshot would only start a chain. Consequences, which the UI must say: undoing the database also drops everything written to the database since the restore, and an undo cannot be undone.
- `file_undo` replays the journal BACKWARDS (`FileUndoer`, byte offset cursor, no memory use whatever the journal size): `O` puts the saved original back (checksum of the saved copy verified first, temp file and rename, the original mtime restored), `C` removes the created file (a regular file only), `D` removes the created folder when it is empty (a folder that holds other files stays and is counted). Every path goes through the same `ExtractionPolicy` and `SafeWriter` rules as the restore (protected paths, symlinks, roots), so a tampered journal cannot reach outside the roots. A missing or damaged saved original is counted (`corrupt_saved`) and that file is left as it is. Result in the job meta (`undo_files`: `restored, removed, folders_removed, folders_kept, errors, skipped`); `finish` marks the original restore `undone_by`.
- `dismiss_undo( $restore_id )` deletes the undo folder (containment-checked: the real path must be `restore-<digits>` directly inside a real folder named `undo`, never a symlink) and marks the restore `undo_dismissed`. It does NOT delete or unlock the safety snapshot backup (it stays locked in History until the user removes it; retention comes later).

### Limits and risks of 5c
- A restore replaces the files of the backup with the versions in it; **core files of another WordPress version** (flag `core`) mix with the files that stay (the preflight already warns about a WordPress version difference).
- A file larger than the free disk space is refused early; a very large file is copied in one go when the original is saved for the journal (`SafeWriter::save_original()` is not chunked across slices; the write of the restored file is).
- tar.gz resume cost (above); the undo journal costs disk space until it is dismissed.
- The destination walk is not safe against an attacker who can swap a folder for a symlink between two system calls (a race); the real-path check after the walk catches a swap that happened before it. Roots are trusted.
- A host where `rename()` cannot replace an open file may leave a window of microseconds without the target (Windows); the original is already in the journal.
- The matrix proves the engine on real WordPress, real databases and real archives (wreck and restore, undo, kills, hostile archives, full disk); there is no REST route or screen yet (step 5d).

## Implemented in Milestone 5 step 5d (the user-facing restore: REST, Restore page, progress, undo)

### REST routes (`Rest\RestoreRestController`, namespace `ovb/v1`)
Every route except the token status route needs `Capabilities::current_user_can_manage_backups()` (`manage_options`, `manage_network_options` on multisite) and the REST nonce (`X-WP-Nonce`, action `wp_rest`; core drops the user of a cookie request without a valid nonce, so the capability check then answers 401/403).

| Method | Route | What it does |
|---|---|---|
| POST | `/restores/preview` `{backup_id, mode, restore_server_config?}` | Runs the same loader and preflight as a start (`RestoreManager::preview()`), creates NOTHING. Returns `RestorePreviewPresenter::build()`: backup facts, which of database / files will be touched, source (local or the destination label), sizes (download, extract, snapshot, journal), disk need against free space, `errors[]`, `warnings[]` (stable codes such as `plugin_protected`, `wp_config_skipped`, `server_config_skipped`), `requires_ack[]` (`url_mismatch`), the protected paths in plain language and the options the page may offer. |
| POST | `/restores` `{backup_id, mode, acknowledge_url_mismatch?, keep_site_urls?, restore_server_config?, confirm_phrase}` | Starts the job (`RestoreManager::start()`, user from the session). It downloads and verifies, then PARKS at `verified`; it never applies. `confirm_phrase` must be exactly `RESTORE` (case-sensitive, no trimming, no look-alike characters): 400 `ovb_confirm_phrase` otherwise, before anything is created. 201 with the status payload plus `status_token` (shown once). A refusal is 400 (preflight error or an unacknowledged `url_mismatch`; `errors` and `requires_ack` are in the error data), 409 for `restore_running` / `backup_running`, 404 for an unknown backup. |
| GET | `/restores/{id}` | Status payload (below). May run ONE slice inline (browser kick). |
| POST | `/restores/{id}/confirm` `{confirm_phrase}` | The second, explicit step after the user saw the final summary. 400 without the phrase, 409 unless the status is `verified` (or a backup is running), then `RestoreManager::confirm()`. |
| POST | `/restores/{id}/cancel` | `RestoreManager::cancel()`; 409 with the refusal text once the restore has started changing the site (the message names Undo restore) or when it already finished. |
| POST | `/restores/{id}/undo` `{confirm_phrase}` | `RestoreManager::undo()` (a new job of mode `undo`, 201 with its payload and a `status_token`); 409 for `already_undone`, `dismissed`, `snapshot_gone`, `journal_gone`, a busy site. |
| POST | `/restores/{id}/undo/dismiss` | `RestoreManager::dismiss_undo()` (deletes the journal; Undo is no longer possible). |
| GET | `/restores` | Recent jobs, newest first, paginated (`X-WP-Total`), small payload. |
| GET | `/restores/{id}/status?t=<token>` | PUBLIC, see "Status token" below. |

Mode is whitelisted to `db`, `files`, `full` (never `undo`); flags are real booleans or `0/1/true/false`; ids are positive integers. Messages are fixed and safe; absolute paths in any message become `[site]`, secrets are masked (`DestinationsRepository::scrub_error()`).

Changed rule (one line): `POST /backups` is now also refused (409) while a restore waits at `verified`, not only while one is queued or running: a backup started in that window would make the confirmation fail (`RestoreManager::confirm()` refuses while a backup runs).

### The status payload (`Restore\RestoreStatusPresenter`)
`id, backup_id, mode, kind (restore|undo), status, phase (preparing|ready|applying|done|failed|cancelled), step, step_label, percent, message, finished, awaiting_confirmation, started_at, finished_at, elapsed_seconds, maintenance (the flag is on), can_cancel, cancel_refusal, snapshot_id, error (scrubbed, paths hidden), warnings[], result, undo_of, undo`. `result` (a complete job): tables, rows, statements, skipped tables, seconds, kept URLs, `files {restored, created, overwritten, bytes, parts, skipped {plain-words reason: n}, skipped_n}`, `undo_files {restored, removed, folders_removed, folders_kept, errors}`. `undo` (a finished, non-undo job): `can_undo`, `reason` (why not), `undo_db`, `undo_files`, `journal`, `undone_by`, `dismissed` and the warning that undoing the database also removes everything written since the restore. The payload never contains an absolute path, a secret, SQL, a statement, row data or the name of the user who started the restore.

### Progress (`Restore\RestoreProgress`, pure)
Bands, monotonic by construction. Restore: preflight 0-3, fetch 3-30, verify 30-40 (a parked `verified` job is 40), snapshot 40-55, db_restore 55-80 (55-95 without files), file_restore 80-95 (40-95 without a database part), finish 95-100. Undo: preflight 0-3, fetch 3-20, verify 20-30, db_restore 30-80 (30-95 without files), file_undo 80-95 (0-95 without a database part), finish 95-100. Inside a band the database import follows bytes read / dump size; steps without a known total follow `n / (n + K)` (growing, never reaching the end of the band); the safety snapshot step has no inner progress. `complete` is 100; failed and cancelled report 0 and the page keeps the highest value it showed. `Engine\Progress` and its backup bands are unchanged.

### Confirmations
Three typed confirmations, all enforced by the server: `RESTORE` to start (download and verify, nothing changes), `RESTORE` again to apply (`/confirm`, only after the final "Ready to apply" summary) and `RESTORE` to undo. The word is not translated.

### Status token and the logout problem
A database restore replaces the users and usermeta tables, so the administrator's cookie and REST nonce can stop working in the middle of the restore (or the user may not exist in the backup). The restore keeps running on the server through Action Scheduler regardless. To keep the progress page honest anyway, `POST /restores` and `POST /restores/{id}/undo` return a 128-bit random `status_token` once; only its SHA-256 is stored in the meta of that job (`status_token`; the `ovb_restores` table survives the import). `GET /restores/{id}/status?t=<token>` needs no cookie and no nonce, is read only (never runs a slice), compares with `hash_equals()`, is valid for that restore id and until one hour after the job finished, sends `Cache-Control: no-store`, and answers an identical 404 for every mismatch (no job, no token, wrong token, expired, route disabled). It returns only `status, step_label, percent, done, failed, message` (the message of a failure is a fixed sentence, never error text). It is reachable during maintenance mode (a route of `ovb/v1`, allow-listed by `MaintenanceMode`; asserted over real HTTP). Filter `ovb_restore_status_token_enabled` (default true) turns the route and the token off. See docs/plan/09-security.md.

### Logout handling in the page (`assets/admin/js/restore.js`)
Polling is authenticated (cookie + nonce). Once the apply started, a 401, 403, 503 or network error is not an error: the script switches to the token channel, keeps the bar moving, shows "You may have been logged out ..." and, when the job is done, "The restore finished. You may need to log in again" with a login link whose `redirect_to` is the Restore page with `&restore=<id>` (full result and Undo after login). A page opened with `&restore=<id>` and no session uses the token kept in `sessionStorage` of that tab. Polling is at most one request per second (2 s, backing off to 8 s on errors) and stops on terminal states and while a job is parked.

### Browser kick
`GET /restores/{id}` runs one `RestoreRunner::run()` slice inline when the job is `queued` or `running` (never `verified`), the restore lock is free and the heartbeat is older than 10 seconds (filter `ovb_restore_kick_after_seconds`), so a host without a working Action Scheduler loopback or WP-Cron finishes while the page is open (asserted over HTTP with both blocked).

### The page and History
Tab "From history" only (a note says that restoring an uploaded archive or a server folder is planned). Steps: choose (restorable backups: complete or partial, not encrypted, newest first, with date and age, trigger label, size, contents and the copies on this server and on destinations; a backup whose only copy needs a reconnect is disabled with the reason; modes only when the backup can satisfy them; multisite disables everything with the exact reason), preview, progress (with the "Ready to apply" gate), result, undo. History gets a "Restore" row action for restorable backups and every plugin page shows a banner "A restore is in progress" (with a link) while a restore is queued, running, parked or the maintenance flag is on. Pure rules: `Admin\RestoreChoices`, `BackupRowPresenter::can_restore()`.

### Limits and risks of 5d
- The safety snapshot step has no inner progress; a large database can sit at 40% for a while.
- A finished restore is reopened from the "Recent restores" list, the banner or its address (`&restore=<id>`), not automatically.
- If a restore needs more than the 30-minute maintenance TTL without a slice, the site fails open (5b rule); the token channel keeps reporting.
- The script only writes text into the page; the chooser list is server rendered and every label (note, destination name) is escaped there.
