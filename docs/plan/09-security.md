# 09 – Security

- **Capability**: `manage_options` (network admin on multisite) for every page, REST route, and AJAX action.
- **Nonces** on all forms and REST calls.
- **Credentials** encrypted at rest (CredentialVault, key from WP salts or `OVB_ENCRYPTION_KEY` constant in wp-config). Secrets never re-displayed in UI (show "••••" + replace button).
- **Local backups**: random folder name, `.htaccess` deny + `index.php`; outside webroot if possible. Warn Nginx users (`.htaccess` ignored).
- **Downloads** streamed through DownloadController only.
- **OAuth state** validation; redirect URI fixed to admin URL.
- **Uploaded archives** for restore: validate it's our manifest, size limits, path traversal checks during extraction (reject `../`).
- **Logs** must never contain tokens or passwords.
- **Standalone restorer**: password protected, random filename, self-delete.

## Implemented in Milestone 2 (CredentialVault)
- **Cipher**: libsodium `sodium_crypto_secretbox` (XSalsa20-Poly1305), random 24-byte nonce per message.
- **Envelope**: `ovb1:` + base64( nonce . ciphertext ). The prefix carries the version; unknown versions fail with `unsupported_version`. Arrays are stored as JSON inside the envelope, never PHP `serialize()`.
- **Key source**: `OVB_ENCRYPTION_KEY` if defined and non-empty, otherwise `wp_salt( 'auth' )` + `wp_salt( 'secure_auth' )`. The 32-byte key is `sodium_crypto_generichash` over `'ovb-vault-v1|' . material`, zeroed after use. `CredentialVault::key_source()` reports `constant` or `salts` for System Info.
- **Failure behaviour**: if the key changes (salts rotated, constant added/removed) decryption fails safely. `decrypt()` throws `VaultException` with a reason (`invalid_format`, `wrong_key`, `unsupported_version`, `unavailable`); `try_decrypt()` returns `[ ok, value, reason ]` for UI code. It never returns garbage and never fatals. On `wrong_key` the UI should tell the user to reconnect the destination. Wrong key and tampered data are deliberately indistinguishable. Messages never contain plaintext, ciphertext or key material.
- **Also built**: `Engine\JobState` (immutable, JSON-only, cursor capped at 64 KB) and `Support\Manifest` (untrusted-input validation: generator, schema, UUID v4, SHA-256, part-name traversal checks, 10,000 parts / 5 MB limits).

## Implemented in Milestone 3 step 3d (DownloadController)
- **Guarantees**: logged-in + `manage_options` (network admin on multisite) + nonce `ovb_download_<file id>`, otherwise 403 with a one-line body. Anonymous requests also get 403 (`admin_post_nopriv_`).
- **Path from the database only**: the file row (destination 0, upload status `done`) and the backup row (status complete/partial) give uuid, creation time and file name; `Backups\BackupFiles::resolve_file()` builds the path under `<local dir>/backups/<folder>` and accepts it only if the name is a plain name, the file is a regular file and not a symlink, and its `realpath` is inside the real backup folder, which is inside the real backups folder. A poisoned row (`../../wp-config.php`, a symlink) gets 404 (tested over HTTP). Request parameters never name a path.
- **Response**: `Content-Disposition: attachment` with a sanitised name, `Content-Length`, `X-Content-Type-Options: nosniff`, no-cache headers, `Accept-Ranges: bytes`, one single `Range` (206; unsatisfiable 416; malformed or multiple ranges are ignored and the whole file is sent), output buffers dropped, 1 MB chunks with `flush()`, session lock released, time limit lifted, stops on client abort. The file is never read into memory.
- **Delete** (`DELETE /backups/{id}`) refuses locked and running backups and removes only a folder whose name matches `<date>_<time>_<uuid8>` directly inside the backups folder (no symlinks followed).

## Implemented in Milestone 4 step 4b (S3 endpoint validation, SSRF)
- **Endpoint rules** (`Destinations\S3\EndpointValidator`, pure): https is required. http only when `allow_insecure_http` is on AND the host is private (loopback, private ranges, `.local` and similar suffixes, or a plain name without dots such as a Docker service). A private host at all needs `allow_private_endpoint`. A public host may only use ports 443, 80 and 8080. No user info, query, fragment or path (a bare `/` is fine), no whitespace, control or backslash characters; host labels are ASCII letters, digits and `-` (IDN in punycode form).
- **IP spellings**: only a clean dotted quad or a bracketed IPv6 address. Decimal (`2130706433`), hex (`0x7f.1`), octal and short forms (`127.1`) are refused outright.
- **Never allowed, whatever the flags**: link-local and cloud metadata addresses (169.254.0.0/16, fe80::/10, fd00:ec2::254, IPv4-mapped forms of these), `metadata.google.internal` and similar names, the unspecified addresses (0.0.0.0/8, ::) and the broadcast address.
- **No global switch**: WordPress's URL safety (`reject_unsafe_urls`) stays on for every request; it is turned off per request only when the validated `allow_private_endpoint` setting is true. Redirects are never followed (`redirection => 0`), so a public endpoint cannot bounce the server to an internal address. Hosts are judged by their form, not by DNS; a public name that resolves to a private address is still caught by WordPress's own check (the setting is off by default).
- **Presets build hosts from validated pieces** (a regex per provider for the region or account id), so a preset can never point outside its provider's domain; a preset ignores a foreign `endpoint` setting.
- **Keys**: every reference must start with `OpenVault-Backups/` and pass `RemotePath::is_safe()`; the prefix setting is limited to letters, digits, `.`, `_`, `-` and `/` without `.` or `..` parts. Nothing outside the plugin's folder in the bucket is reachable.
- **Secrets**: the secret key lives only in the signer (hidden from `var_dump` and `print_r`). Error messages are fixed texts with a sanitised S3 code; server error bodies are never copied, XML is parsed with DOCTYPE and entity declarations refused, `LIBXML_NONET` set and (PHP below 8) entity loading disabled.

## Implemented in Milestone 4 step 4c (secrets are write-only)
- **No re-display**: the Destinations form never renders the access key or the secret key, not even in a `value` attribute. Editing a destination shows that keys are saved and offers to replace them; leaving the fields empty keeps the stored ones. `GET /destinations` is built by `DestinationPresenter` from a whitelist and the repository never selects the credentials column for normal reads, so a response cannot carry them (it only says `has_credentials`).
- **Server-side only**: credentials are decrypted in `DestinationRegistry::create()` for a test or an upload and nowhere else. Write path: `DestinationSettings::validate_credentials()` (shape and length) then `CredentialVault` encryption (`ovb1:` envelope). If encryption is unavailable nothing is saved.
- **No leaks**: validators never put a submitted value in a message; test failures pass through `DestinationsRepository::scrub_error()` before they are stored or returned; the logger records only ids and types for destination changes. The matrix greps REST responses, page HTML, `debug.log`, the Apache log and the plugin log table for the real and a wrong secret.
- **Every route**: capability (`manage_options`, `manage_network_options` on multisite) and the REST nonce; anonymous 401, no nonce 401, bad nonce 403, subscriber 403.
- **Unsafe input is refused, not trimmed away**: unknown keys, endpoints that fail the SSRF guard (also on update, where a refused update changes nothing), `..` or absolute prefixes, local folders that are the WordPress root, wp-admin, wp-includes, the tmp folder, relative or contain `..`.
- **Removal** deletes the row and its credentials. Remote files are never deleted by removing a destination, and removal is refused (409) while a queued or running backup uses it.

## Restore engine (Milestone 5 step 5a)
- Files fetched or read for a restore are untrusted until verified: the manifest goes through `Manifest::from_json()` (strict, rejects traversal, error messages never echo it) and must carry the backup's uuid; every part is checked against the manifest and database checksums before anything may be applied. A manifest of a newer schema, an encrypted backup and a different table prefix are refused.
- File names inside the restore work folder come from the manifest/database rows but still go through `RestoreWorkDir::join()` (plain names only). Only `<local dir>/tmp/restore-<id>/` is ever removed, with a pure path check, a realpath comparison and a symlink refusal; the plugin's tmp area is never wiped wholesale. The folder gets the same guard files as every protected plugin folder. Downloads never use a public URL.
- A restore changes nothing without the user's confirmation: the job stops at status `verified` and only continues when its meta holds `confirmed = true` (set by the confirm action of step 5c, which must check capability and nonce like every REST/AJAX/page action; step 5a has no REST or UI at all).
- A different site address needs an explicit acknowledgement (`acknowledge_url_mismatch`), stored in the job meta; an acknowledgement never overrides an error.
- Credentials are only decrypted in `DestinationRegistry::create()`. Errors from destinations are scrubbed (`DestinationsRepository::scrub_error()`) before they reach the job state, the restore row, or the logs, and messages contain no server paths.

## Database restore (Milestone 5 step 5b)
- **The dump is untrusted input.** A backup can sit in a bucket or folder that somebody else can write to, and the restore runs its statements with the full rights of the site's database user. The checksums do not help: someone who can rewrite a part can rewrite the manifest and the checksums too. So `Restore\DumpValidator` (pure, tested with a large hostile corpus) accepts only the exact statement shapes that `SqlDumpWriter` writes and nothing else (details in docs/plan/08-restore.md): no stacked statements (the VALUES list is read with a real tokenizer), no comments or executable comments, no `SET GLOBAL`/user/privilege/trigger/routine/event/view statements, no `INTO OUTFILE`/`LOAD_FILE`/`LOAD DATA`, no foreign storage engines, no table outside the site's prefix and no plugin table (`<prefix>ovb_*`, any letter case). Lines are bounded (4 MB), UTF-8, without NUL or CR.
- **Validate everything, then execute.** A validation pass judges every line without executing anything, so a refused line stops the restore at its line number before a single table was touched; the import judges every line again. Refusal messages are fixed texts with the line number: never a statement, a value or a name from the dump. Database errors are reduced to the MySQL error number (`WpdbExecutor`): `$wpdb` messages can contain row data, so they are never stored, shown or logged.
- **Only one entry is read from an archive**, by an allow-list of one name (`db/db.sql`) that is also checked for `..`, absolute paths, backslashes and NUL (`Archive\ArchiveReader`); links, folders and look-alike names are never extracted. The database part is hashed again just before it is unpacked.
- **The plugin protects itself**: its tables and the Action Scheduler tables are never dropped or replaced, its options are written back and read back after the options table is swapped (`SelfPreserver`), and the job state lives in `ovb_restores`.
- **Maintenance mode** is a plugin flag with a 30-minute failsafe expiry (fails open), gated per request by a pure allow-list. The plugin's REST namespace is recognised from the URL path or the `rest_route` parameter only, never from other query values. Admin area requests during the restore need `manage_options`; the plugin's own routes keep their usual capability and nonce checks.
- **Credentials**: nothing about destinations is read or logged by these steps. The saved plugin settings are held in a private file in the restore work folder (guarded like every plugin folder) and removed with it.
- Step 5b has no REST route or screen: the capability and nonce checks for `confirm`/`cancel` belong to step 5d, which must also tell the user that cancel is refused once the import has started.

## File restore and undo (Milestone 5 step 5c)
- **The archive is untrusted, so is the destination.** The extraction rules (`Restore\ExtractionPolicy`, `Restore\SafeWriter`) are in docs/plan/08-restore.md; in short: names with `..`, absolute names, backslashes, control or bidirectional characters, drive letters, overlong names, trailing dots and spaces are rejected; symlinks, hardlinks and devices in an archive are never extracted; every folder below a root is walked without following symlinks and a symlink is refused; the real path of the destination must stay inside the real path of the root; files are written to a temp name (exclusive create) in the same folder and renamed, with no execute bit.
- **The plugin protects itself and the site**: its own folder, its storage folder (and any `wp-content/ovb-*`), `wp-config.php`, `.maintenance` and the server configuration files of the WordPress folder are never written (a self-test checks this before the first write); `restore_server_config` is an explicit opt-in and never covers wp-config.php.
- **Nothing outside the roots of the backup is touched**, and nothing is deleted by a restore.
- **Undo data is protected like backups**: it lives in the plugin's protected storage folder (guard files, never archived, never a restore target) and is read back through the same rules: absolute paths are never stored, every journal name is validated, the journal's contents flags (not paths) give the roots, saved originals are verified by SHA-256 before they are put back, and a tampered journal cannot reach protected paths, symlinks or anything outside the roots. A hostile archive name can never break the journal format (control characters are refused; skip lines are URL-encoded and cut).
- **Logs and results hold no content**: a skipped entry is logged by its number and a cleaned, 80 byte name (control and bidirectional characters replaced); results hold counts by reason only.
- **Capability and nonce** checks for `confirm`, `cancel`, `undo` and `dismiss_undo` belong to the REST routes and screens of step 5d (`manage_options`, network admin on multisite; a nonce on every action). `undo` and `dismiss_undo` are destructive and must be confirmed in the UI.

## Restore screens and REST (Milestone 5 step 5d)
- **Capability and nonce** on every restore route (`RestController::permission()`: `manage_options`, network admin on multisite; the REST nonce on every cookie request) and on the Restore page. Asserted over real HTTP: no nonce 401/403, bad nonce 403, anonymous 401, a subscriber with a valid nonce of his own 403.
- **A stray or forged POST cannot change anything**: starting, applying and undoing each need the typed word `RESTORE` in the request body (server side, exact match), on top of the nonce. A CSRF request has no nonce; a request with a valid session but no phrase is a 400 that creates nothing.
- **Unauthenticated status channel** `GET /ovb/v1/restores/{id}/status?t=<token>`. Why it exists: a database restore replaces the users and sessions tables, so the administrator may be logged out mid-restore and the page could not tell the user what is happening. What it exposes: `status`, `step_label`, `percent`, `done`, `failed` and a short fixed message, nothing else (no ids, no error text, no paths, no counts). Why that is acceptable: the token is 128 random bits created per job and shown once to the browser that started it; only its SHA-256 is stored (a database leak does not give the token); it is compared with `hash_equals()`; it is valid for one restore id only and stops working one hour after the job finished; every mismatch is the same 404 (ids cannot be probed); it is read only (never advances a job); responses carry `Cache-Control: no-store`. The worst a stolen token allows is watching a progress percentage for at most an hour. How to turn it off: `add_filter( 'ovb_restore_status_token_enabled', '__return_false' );` (no token is created, the route answers 404; the page then waits for the user to log in again).
- **No leaks**: payloads are built from whitelists (`RestorePreviewPresenter`, `RestoreStatusPresenter`); absolute server paths become `[site]`, error text is scrubbed, no SQL, statements, row data, tokens, credentials or user names are returned. Unit tests assert this with canary strings; the HTTP tests grep real responses and pages.
- **XSS**: the Restore page escapes every label on the server (backup note, destination label); the script writes text only (`textContent`). A hostile note and destination label are planted in the HTTP tests and must appear only escaped on the Restore page and in History.
- The "Restore" action and the banner on every plugin page need the same capability as the pages.
